# 通行密钥卡牌图鉴与稀有卡解锁计划

## 1. 目标与现状

玩家默认拥有全部非稀有卡；登录后，同一把通行密钥在钱包之外恢复专属的图鉴加密密钥与同步身份，从项目托管的 D1 密文恢复已获得的稀有卡。只有本场开局时已拥有的卡能进入本场发牌池。已登录玩家完成比赛后按下注档位抽取一次稀有卡奖励；只有首次获得新卡时才在结算页上层播放获得动画。拥有状态是集合，不记录卡牌数量。

本计划的稀有卡属于**个人游戏进度**，不代表可交易资产或已由链上验证的奖励。当前 `src/chain/mock.ts` 本地生成 seed、扣款和结算；浏览器产生比赛结果。Worker 只看密文，无法证明比赛发生过、下注真实支付或奖励抽签没有被客户端修改。界面与提交材料必须如实说明这一边界；有奖版本的稀有卡获得资格必须来自 PonyGame 已最终确认的结算事件及可验证的奖励规则，不能把本计划的加密同步当作防作弊机制。

当前代码的直接冲突：`src/race/cards/pool.ts` 有 21 张卡，其中 9 张 `common`、12 张 `rare`；`src/race/core/deck.ts` 要求玩家牌堆 14 张互不重复，末两张必为 `rare`。默认只解锁 9 张非稀有卡时，现行发牌算法无法工作。第 3 节明确修改这一规则，不以空牌、暗中放出未解锁稀有卡或新增卡牌填数。

## 2. 玩家流程与状态

1. **访客**：可以用默认非稀有卡试玩，图鉴只显示已公开的非稀有卡；稀有卡显示锁定占位，不显示详情。访客不参与稀有卡奖励，选马页和结算页明确提示“登录后可获得稀有卡”。下注仍走现有本地 mock，0 MON 档也可玩。
2. **注册或登录**：沿用 `src/chain/wallet.ts` 当前 Mera 钱包动线。登录成功并确定系统实际选中的 credential ID 后，再由同一把通行密钥分别取得图鉴加密命名空间和同步身份命名空间的 PRF 输出。图鉴状态在同步、解密和校验完成前为“加载中”，不能先以空集起跑，避免覆盖已有收藏。
3. **图鉴恢复**：客户端向同源 Worker 证明持有图鉴身份私钥，读取 D1 中的密文，在浏览器中解密；服务端始终看不到拥有的卡牌 ID。首次没有记录时，以空稀有卡集合作为内存状态；默认非稀有卡由本地配置补齐，首次成功写入后才显示“已同步”。解密失败、未知版本或网络失败均保留原密文，给出重试，不把它当成新账户初始化。
4. **开局**：将 `默认非稀有 ID ∪ 已拥有稀有 ID` 及卡池/发牌规则版本冻结为本场快照，传给规则内核。比赛中途登录、退出或另一设备解锁卡牌均不改变这场比赛的牌堆。下一场才读取新快照；加载失败的已登录账户不可开有奖励的比赛，访客试玩入口仍可用。
5. **完赛与奖励**：免费 Demo 仍以整场完成且本地 `settleRace` 成功作为展示入口；有奖版本只以 PonyGame 已最终确认的结算事件和可验证奖励资格作为入口。免费 Demo 仅已登录且开局绑定了该通行密钥身份的场次参与；同一 `raceId` 只处理一次。依配置先判定是否命中奖励，再从尚未拥有的稀有卡按权重抽取一张；没有剩余稀有卡、未命中或 0 MON 档均无新卡。使用浏览器安全随机源，不能用比赛 seed、`Math.random()` 或重复加载结算页重新抽签。
6. **保存与展示**：将新卡 ID 加入集合，在浏览器中重新加密，以 D1 版本号做条件更新。只有远端确认新集合写入成功，才把卡设为已获得并在结算页上层播放一次获得动画；没有新卡时只显示普通结算。写入超时或失败时保留**仅含密文**的本地待同步记录并显示“奖励待同步/重试”，不播放获得动画，不把失败误报成已获得。再次进入或刷新页面须先读取远端版本、合并待同步奖励，再决定是否展示；已被另一设备加入的卡不再播放首次获得动画。
7. **跨设备**：设备 B 使用同一站点域名、同一把已同步到设备 B 的通行密钥登录，重新取得相同命名空间输出，经身份验证从 D1 取回密文，解密后看到设备 A 的卡牌；B 不需要 A 的浏览器存储、助记词或私钥。更换域名会更换 WebAuthn `rpId`，需在部署前固定正式域名。

## 3. 卡池、发牌与奖励配置

配置只保留一个真源，与 `CARD_POOL` 中稳定的 `cardId` 关联：

| 配置 | 内容与维护规则 |
| --- | --- |
| 默认解锁列表 | `quality !== 'rare'` 的全部 `cardId`，由卡池定义派生；新增非稀有卡自动进入默认集合，改品质必须走规则版本审查。不在每个用户密文中重复存默认卡。 |
| 下注档位 | 引用 `src/race/core/constants.ts` 的 `STAKE_PRESETS` `[0, 1, 5, 10]`；概率表按档位值关联，不依赖数组位置。 |
| 奖励概率与卡牌权重 | 集中放在一份独立的卡牌进度配置中；静态校验覆盖全部下注档位、全部 `rare` ID，禁止未知/重复 ID、负值和超出 `0..10000` 的概率。修改表时提升奖励配置版本；已经获得的卡不回滚。 |

第一版明确采用以下基线数值。`命中概率` 的单位为万分之一；命中后只在**尚未拥有**的稀有卡中按相应权重抽取。权重不是直接概率，当前可选集合变化后要重新归一化。

| 下注 MON | 命中概率 | `C-10` 史瓦西黑洞权重 | 其他每张未拥有稀有卡权重 |
| ---: | ---: | ---: | ---: |
| 0 | 0 / 10000 | 0 | 0 |
| 1 | 1000 / 10000 | 1 | 10 |
| 5 | 2500 / 10000 | 4 | 10 |
| 10 | 4000 / 10000 | 12 | 10 |

“其他稀有卡”当前为 `C-02、C-03、C-04、C-05、C-06、C-09、C-11、C-13、C-16、C-18、C-21`。配置中仍逐卡列出权重，表格可以按组展示。以全部稀有卡均未拥有为例，`C-10` 在 1 MON 档的单场概率是 `0.10 × 1/111`，在 10 MON 档是 `0.40 × 12/122`；两者随下注提高而增长。改动稀有卡清单时，配置校验必须要求显式补齐权重，不能静默采用默认值。

**发牌规则变更**：保留 14 个有序牌位和每检查点 3 张候选，但把“整副牌绝不重复”改为“单轮池内无放回；池耗尽后按同一 seed 的下一轮重新洗牌”。因此初始 9 张非稀有卡可填满 14 个牌位，跨轮可以重复；同一次三选一不得出现相同 `cardId`。玩家牌堆与 CPU 私有牌堆都从本场解锁快照过滤，绝不抽到锁定卡。末尾稀有保底只在已解锁稀有卡中选：拥有 0/1/至少 2 张时分别预留 0/1/2 个末尾位置；其余位置按前述轮次填充。原有刷新、游标前进和卡牌效果必须在池轮换边界继续有效。此改动提升 `rulesVersion`，更新发牌向量、规则测试和可回放记录；旧结果按旧规则版本解释。

图鉴“锁定”仅指应用正常界面不展示详情、规则内核不抽取。卡牌定义仍在前端包内，不能宣称代码层面的保密。稀有卡拥有状态与奖励表分离：**拥有是布尔集合，永不累加数量**；重复同步同一张卡是幂等操作，不会触发动画。

## 4. Mera 命名空间与加密

继续使用当前 `@category-labs/mera`、WebAuthn PRF、`@scure/*`、viem 与浏览器 Web Crypto。钱包原有默认 PRF salt 与地址派生路径保持不变；绝不能从钱包私钥、钱包助记词或默认钱包 PRF 输出推导图鉴密钥，也不能为图鉴另建一把通行密钥。

在同一 credential 上分别调用 Mera `getPasskeyPrfOutput({ rpId, credential, prfSalt })`：

| 用途 | 固定 32 字节 salt 的定义 | 输出用途 |
| --- | --- | --- |
| 图鉴加密 v1 | `SHA-256("ponygogogo/collection/encryption/v1")` | 以 HKDF-SHA-256 和固定用途标签派生不可导出的 AES-256-GCM 密钥；只在浏览器加解密。 |
| 图鉴同步身份 v1 | `SHA-256("ponygogogo/collection/identity/v1")` | 用 Mera 的 `createEd25519SigningSession` 得到独立于钱包地址的公钥和短时签名会话；公钥哈希作为 D1 用户索引，公钥用于 Worker 验签。 |

WebAuthn 调用必须限定当前登录凭据，核对返回的 credential ID，防止同一域名下多把通行密钥混用；跨设备时先通过现有登录流程确定该凭据，不依赖设备 A 的本地记录。Mera 每次 PRF 断言可能再次弹出系统验证，界面需要单独呈现“解锁图鉴”，不能暗示钱包登录必然一次提示就完成所有操作。退出登录结束钱包与图鉴签名会话、清除明文集合和可清零的 PRF 字节；刷新后重新验证。密钥、PRF 输出、助记词、明文收藏均不写入日志、`localStorage`、IndexedDB、D1 或分析服务。

加密载荷只保存稀有卡 ID 的去重排序集合、数据格式版本、卡池版本、奖励配置版本和用于本地幂等处理的比赛 ID；默认卡不存。每次写入生成新的 96 位随机 IV，采用 AES-GCM，并把用户索引、文档类型、格式版本与目标 D1 版本作为附加认证数据。D1 保存 `userId`、Ed25519 公钥、记录版本、加密格式版本、IV、密文和更新时间；服务端不解密。读取时先检验格式与版本，再解密、校验 ID 全属于对应版本的 `rare` 卡池并规范排序；未知卡池版本不可静默丢卡，应保留原记录并提示升级客户端。只有密文和公开元数据允许作为本地待同步记录持久化。

## 5. Worker、D1 与并发

当前 `wrangler.toml` 只有静态资源。为同源 `/api/collection/*` 增加 Worker 脚本与 D1 binding，仅对 API 路由先运行 Worker，其他请求继续走静态资源；更新本地开发、部署脚本与数据库迁移步骤。Cloudflare 官方支持静态资源 Worker 按路由优先处理 API、D1 Worker binding 与 WebCrypto Ed25519 验签。正式域名、RPC、D1 预览库和生产库应分别核对，不能把本地/预览数据误写生产库。

接口契约：

| 接口 | 请求与响应 | 核心规则 |
| --- | --- | --- |
| `POST /api/collection/challenge` | 请求公钥；返回一次性随机 challenge、过期时间与 challenge ID | 2 分钟有效，D1 原子消费，限制体积与请求频率；无收藏数据。 |
| `POST /api/collection/read` | 公钥、challenge ID、签名；返回 `404` 或当前 `version + envelope` | 验证签名覆盖域名、方法、路由、challenge ID 和请求摘要；用公钥哈希查该身份的数据。 |
| `PUT /api/collection` | 公钥、challenge ID、签名、`expectedVersion`、加密 envelope；返回新版本 | 签名覆盖密文哈希与期望版本；D1 做条件更新。版本不符返回 `409` 和当前版本，绝不盲写。新纪录只允许从版本 0 创建。 |

挑战只能消费一次，读取与写入分别取新挑战；签名不能重放到别的请求或用户。Worker 不把地址字符串当作身份认证，不接收明文卡 ID，不持有解密密钥；设置同源限制、`Cache-Control: no-store`、请求体上限和基本限流。密文读权限由图鉴身份公钥签名控制，公钥本身不是秘密。D1 写入必须检查 `expectedVersion` 并以受影响行数确认成功；必要时用唯一键约束首次创建的并发冲突。

遇到 `409`：客户端重新获取并解密远端版本，对稀有卡集合做并集，再以新版本重加密重试。待领取奖励必须保留本场 `raceId` 和一次抽签的随机材料；并发合并后若原抽中的卡已由另一设备获得，按**同一次命中**在新的未拥有集合中重新选卡，不能重新进行命中判定或额外增加一次机会。全部收齐后记录为无新卡；每次可见动画只在最终确认的集合中确实新增该 ID 时触发。连续冲突达到 3 次后停止自动重试，显示手动重试，不丢失本地加密待同步记录。

奖励的命中判定和加权选择都从安全随机源取均匀整数；当随机值范围不能被总权重整除时采用拒绝采样，避免取模偏差。待同步记录先在浏览器加密后才落入 IndexedDB；其中包含同一次抽签的材料、比赛 ID、目标新卡和原版本，重启后先与远端核对再重试。服务端即使验证签名，也只能证明“某个图鉴身份发起写入”，不能证明卡牌获得是否合法。

结算页新增独立的获得卡片浮层，覆盖现有 1620×971 结算画板但不改变名次、返还和原有按钮布局。动画只消费“远端确认且本次确实新增卡 ID”的事件，先显示卡背，再翻出卡面和名称，最后可关闭；关闭、跳过、切换页面或开启减弱动效均不改变已保存状态。浮层资源加载失败时仍以静态卡面和名称完成展示。奖励未命中、已全部集齐、访客、重复回执或同步失败均不能进入获得动画状态。

现有 `RaceResult` 只含 seed 和选择记录，没有本场可用卡集合；引入私有解锁池后，单凭 seed 已无法公开复算完整发牌。Demo 把冻结的可用 ID 列表、卡池版本和规则版本保存在本场内存与加密的个人记录中，用于本地回归。有奖版本要链上重放比赛，必须公开本场可用卡集合并核验资格，或提供链上可验证的成员/资格证明；仅有卡集合哈希不够；不能同时宣称“收藏完全私密”和“仅凭当前链上 seed 可公开重放”。

## 6. 代码改动位置与实施顺序

| 阶段 | 改动位置 | 完成判据 |
| --- | --- | --- |
| 1. 规则红线 | `src/race/core/deck.ts`、`engine.ts`、`driver.ts`、`types.ts`、`constants.ts`、卡池配置及现有规则/向量测试 | 先写默认 9 张非稀有可生成 14 位牌堆、无锁定卡、三选一不重复、CPU 同快照、0/1/2 张稀有末尾规则的失败用例；修复后全绿，旧规则按版本可区分。 |
| 2. 图鉴与奖励 | 独立的卡牌进度模块、`CollectionScreen.tsx`、`App.tsx`、`ResultScreen.tsx`、中英文文案及样式 | 默认卡可见、稀有锁定；奖励概率/权重静态校验；只在新卡远端确认后出现位于结算页上层的独立动画，关闭/跳过和减弱动效不影响保存。 |
| 3. 加密身份 | `src/chain/wallet.ts` 邻接的图鉴会话模块与独立单元/契约测试 | 同一凭据两种新 salt 均可跨会话重现；与钱包 PRF 互不相同；选错凭据、无 PRF、登出、解密失败、未知格式均拒绝或可恢复，不写明文/密钥。 |
| 4. 同步服务 | 新 Worker、D1 迁移、`wrangler.toml`、开发/部署流程和 API 测试 | 验签、一次性 challenge、首次创建、读取、条件写入、`409` 合并、超限和错误返回均通过；API 只存密文与公开元数据。 |
| 5. 真实验收 | 浏览器端到端与两台真实设备/全新浏览器配置 | A 解锁新卡并看到一次动画；B 用同一通行密钥解密同一集合并在下一场抽到该卡；不同通行密钥无法读取或解密；断网待同步恢复、并发写、重复结算不重复获取；记录浏览器、系统和通行密钥提供方。 |

每阶段按“写出真实失败用例 → 看见红线 → 修复 → 全绿”执行。虚拟认证器与假 D1 可验证协议和 UI 路径，不能替代真实设备 PRF、正式域名及 Cloudflare 线上读写验证；上线前另测一次真实跨设备闭环。若 PRF 提供方未将通行密钥同步到 B，B 无法恢复，界面必须指出这一前提。

## 7. 成本与运行边界

项目承担 Worker 请求、D1 行读写与密文存储成本，不需要为每次图鉴更新支付链上 gas。按当前 Cloudflare 文档，Workers 免费计划是每日 10 万请求，D1 免费计划是每日 500 万行读取、10 万行写入及总计 5 GB 存储；超限行为和价格以部署时官方页面为准。上线后记录 API 成功率、`409`、请求量、D1 行读写与存储量，超过免费额度或出现频繁冲突时再调整服务等级。一次打开图鉴只读一次，获得新卡才写一次；比赛 tick 和卡牌动画均不请求同步接口。
