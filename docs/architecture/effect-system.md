# 效果系统与事件求时器架构

`src/race/` 是浏览器端的规则参考实现，用于预览与测试比对；Solidity 复算同一冻结规则（[总体架构](overall.md)）。本文定规则层内部的边界：**规则表、求时器与表现层**。卡牌设计在[卡牌与效果系统设计](../card-design.md)，本文只定边界、扩展点与确定性约束。

## 1. 为什么只有一个求时器

卡牌会长期增长，[卡牌设计 §3](../card-design.md) 的原语包含场上实体、区域场、全局环境、自动触发、监听与发牌游标。如果每张卡自带一段结算逻辑，每加一张卡都可能改变既有卡牌的事件边界或积分函数，浏览器与 Solidity 也要逐张对齐。因此：

- 卡牌的数值与资格只存在于一张规则表（`src/race/paid/cardRules.ts`），Solidity 表由它生成；
- 事件边界、同刻顺序与积分只存在于求时器（`src/race/paid/solver.ts`）。一场比赛只有这一套求解，免费试玩与有奖比赛共用它；
- 新的效果机制先进入求时器与规则版本，再进入规则表。

判据是**这段逻辑在卡池为空时还需不需要存在**：需要的（运动、体力、里程、冲线、发牌、名次）是求时器的固定部分，不需要的（某些卡才会发生的事）用效果实例表达。

## 2. 求时器的固定部分

求时器在卡池为空时也能独立跑完一场五匹马的比赛。它包含且只包含：

| 职责 | 说明 | 位置 |
| --- | --- | --- |
| 事件求时与处理顺序 | 有序事件表、无场解析积分、有场确定性数值积分，见 §5 | `paid/solver.ts` |
| 马匹运动学 | 运动基础速度按加速度与上限计算；固定速度 B 加入 b 后乘百分比，额外速度 K 外加；玩家力竭钳运动基础速度到1200、加速度0，S=135退出；对手规则保留 | paid/motion.ts |
| 体力与资源 | 当前代码按时间消耗和恢复，玩家常规容量300（奶龙400）、消耗20/s、恢复10/s；直接补给可超容量，持续恢复有上限；玩家overcap消耗减半且不恢复，对手overcap消耗不减半且不恢复。距离消耗规划仅记录于数值规划 | paid/motion.ts、paid/resources.ts |
| 里程与终点 | `dist` 积分、25% / 50% / 75% 里程档触发、`pos ≥ L` 的首次冲线时间、物理排序与经验证的彩蛋结算排序 | `paid/solver.ts`、`core/paidSettlement.ts` |
| 入场派生 | 玩家 14 张牌堆、电脑马各 3 张私有牌与五马性格，由 seed 与入场锚经域分离派生；这是唯一随机源 | `core/paidDeck.ts`、`paidCpuDeck.ts`、`paidProfiles.ts`、`chainEntropy.ts` |
| 发牌状态 | 游标、刷新额度、自动与断卡，以及已存选择的合法性判定 | `core/paidDrawRules.ts` |
| 效果实例容器 | 实例的挂载、计时与带原因的结束（到期、覆盖、偷取、回收、消费、冲线） | `paid/solver.ts` |
| 速度与体力聚合 | 对每匹马把当前有效实例求和成百分比贡献、体力消耗与恢复修正；门控实例按当前条件计入 | `paid/solver.ts` 的 `mods()` |
| 事件日志与摘要 | 每个处理的事件按事件码折叠进 `digest`，与 Solidity 逐项一致 | `paid/events.ts` |

**效果容器与速度聚合归求时器，不归某张卡。** 它们是全部卡牌共用的基础设施；让每张卡各自实现时间边界与数值舍入，会导致两端结果不一致。

**里程也归求时器**，即使卡池为空它仍然要算——检查点抽卡是玩法骨干，不是某张卡的效果。

**电脑马与玩家马共用同一运动公式。** 性格与三张私有牌由入场锚确定，私有牌在其里程档自动生效；没有追赶项、目标速度或噪声。

## 3. 效果实例

一张卡的全部数值在规则表的一行（`PaidCardRule`）。`applyCard` 按该行的 `effect` 分支，把它展开成实例或一次性写入。实例的种类：

| 种类 | 含义 | 代表卡 |
| --- | --- | --- |
| `buff` | 限时的百分比、体力修正或状态标志（起飞、亢奋、运气E）。门控实例在每个运动区间按起飞、已获得毛发颜色数量或装备条件重算贡献 | C-01、C-02、C-25 至 C-29、C-33 至 C-36 |
| `bonus` | C-04 之后获得的卡附带的 `P +2000` | C-04 |
| `equip` | 占装备槽（躯干、尾、四蹄）；重力井作为带场标记的装备存在；到期、被覆盖、被偷、被回收时结束，刷新只更新期限 | C-07、C-08、C-10、C-11 |
| `ability` | 周期性自动触发的能力 | C-09 |
| `respawn` | 死亡后 5000 ms 的免疫 | 系统自持 |
| `watch` | 监听：等待阶段边界、资源阈值、独立里程阈值、装备获得、死亡拦截、力竭拦截或主动放弃，触发后更新自身或挂载新实例；永久监听到消费为止 | C-23、C-24、C-31、C-37 至 C-40 |
| `fixed` | 有来源与期限的额外速度 K，死亡保留，到期移除 | C-22 |

不属于实例、直接记在马或场上的状态：当前显示毛色与已获得毛发类型集合（C-19/C-20）、固定速度 B（C-17/C-18/C-21；C-40各阶段由监听更新）、目中无人、断卡和C-04附加标记；全场风槽与炸弹列表。风火轮K属于装备实例，移除即清除；死亡不改上述卡牌状态。

实例上限 96、炸弹上限 20、事件上限 4096。超出时求时器抛错，不静默截断；合法输入不会触及上限，已存选择也不会让求时器抛错。

交换同时置换两匹马的 `pos` 与 `laneIndex`：`horseId` 仍是身份，`laneIndex` 是可变的上下站位，渲染层按它画在第几行（[玩法设计 §2](../game-design.md)）。速度、里程和同刻冲线排序不读取 `laneIndex`。

规则表缺卡或越界在使用时失败：`paidCardRule` 对越界 id 抛 `INVALID_PAID_CARD`，卡面缺元数据抛 `MISSING_CARD_METADATA`，`scripts/gen-paid-card-rules.ts` 校验 id 连续与卡池下限。

## 4. 扩展点与写入边界

### 4.1 新增一张卡

- 机制已有：在 `cardRules.ts` 加一行，在 `src/race/cards/metadata.ts` 加名称、梗源与图标；说明文字由规则表生成。重新生成 Solidity 表与向量，规则版本随卡表哈希变化。
- 引入新机制：先在 `cardRules.ts` 加 `effect` 与字段，在 `solver.ts` 的 `applyCard`、`mods()`、`triggerAt`、`findDue` 加分支，同步 `contracts/libraries/PaidRaceEngine.sol`、`PaidRaceCardPlan.sol` 与 `PaidRaceMotion.sol`，再生成向量，最后部署新的求时器与 Game。如果一张新卡逼着你改同刻顺序或积分函数，说明它需要第十类原语，先回[卡牌设计 §3](../card-design.md) 论证，再改本文，最后才加卡。

### 4.2 速度与体力是聚合出来的

`mods()` **返回**当前时刻的百分比贡献、体力消耗与恢复修正，不直接写速度：返回值可以按固定顺序求和，写入则依赖调用次序，而调用次序是最容易在重构中悄悄改变的东西。聚合按[卡牌设计 §3.2](../card-design.md)：

- 百分比先加总、只乘一次 b=b_motion+B；B参与乘法，K在乘法之外。贡献只在挂载、触发或结束时增减，死亡保留；
- 重力井的场项在积分内部按同一求解时刻的五马实时位置计算，不取触发时的快照；
- 卡牌不修改基础加速度；固定速度B独立于运动基础上限。玩家与CPU力竭的有效加速度为0，运动基础速度钳至1200，不清除B/K；死亡或解除力竭后的恢复加速度为150，达到各自上限后清除恢复状态，冻结性格不被改写。

### 4.3 写入边界

这张表是[玩法设计 §6](../game-design.md) 那条硬约束的实现落点：每类状态只有列出的位置能写，其余路径只读。

| 写入对象 | 唯一写入位置 |
| --- | --- |
| 任意马的 `pos`、`dist` | `advance` 的运动积分；`pos` 另可由 `swapAttempt` 置换，**`dist` 从不被交换改写** |
| 任意马的 `laneIndex` | `swapAttempt` |
| 基础速度、体力 | `advance` 的积分与阈值事件、`kill`、`recover` 与 `applyCard` 的体力写入 |
| 恢复加速度状态 | kill、力竭解除设置150；达到运动基础上限时清零；冻结accel保持只读 |
| 固定速度 B / 额外速度 K | applyCard、实例挂载与结束、风火轮档位与里程监听；kill保留两池 |
| 当前毛色、历史毛发种类、装备槽、风、炸弹 | applyCard、equip / steal / endInstance、placeBombs 与炸弹触发 |
| 牌堆游标与刷新额度 | `core/paidDrawRules.ts` 的 `applyPaidChoice`、`resolvePaidAutomaticChoice` |
| 结算排序 | `core/paidSettlement.ts`：只读 `finishTime` 与已获得卡牌集合，不改 `finishTime`、`rawOrder` |
| 五马入场冻结的基础加速度、速度上限与体力参数 | **无**：`createState` 之后只读 |
| gogo 与镜头 | **无**：`PaidCoreInput` 没有对应字段 |
| 渲染层状态 | **无**：求时器不 import Phaser、React 或资源清单 |

**跨马写入是双向的**（[卡牌设计 §2.1](../card-design.md)）：玩家的卡能写电脑马，电脑马的卡也能写玩家。唯一禁死的是性格参数那一行——它们是难度标定的锚点，可写就连定性分类都不剩了。

「`dist` 只由运动积分累加」是里程制免疫刷卡的实现保证：只要没有任何卡能写里程，就不存在任何一张卡能凭空制造抽卡机会。这条比逐张卡去防可靠得多。

### 4.4 【力竭】

力竭属于马的体力状态。玩家S见底时，亢奋保证下限1；30s内未消费的来劲先拦截一次并恢复250，否则记EXHAUST_ENTER、停止消耗、加速度0、运动基础速度钳至1200。S恢复到135时记EXHAUST_EXIT，开放常规上限但不改变当刻速度。获得亢奋可解除已有力竭；直接补给达到退出阈值也可解除。CPU同样采用基础限速1200、恢复15/s与退出体力135。死亡或解除力竭后，玩家与CPU以150加速度恢复至自身运动基础上限，再还原冻结性格的常规加速度。

## 5. 确定性与阶段顺序

确定性靠输入显式、全整数运算与冻结的事件顺序：

- **输入全显式。** `PaidCoreInput` 是求时器的全部输入：五马性格、两类牌堆、seed、入场锚与已存选择。求时器不读系统时钟、不 `Math.random`，随机一律走 `chainEntropy` 的域分离派生，绑定 seed、选择交易的可验证区块哈希、检查点、用途与事件序号（[架构 §4](overall.md)）。
- **全整数。** 时间为整数毫秒，位置、里程、速度与体力为定点整数（`bigint`）；所有循环有界，求不出进展时抛 `NO_PROGRESS`。
- **规则版本。** 当前名单规则哈希由 v8 域、卡表、pony表和玩家基线哈希共同生成，公式以 cardRules.ts 为准；表或全局参数变化必须升级生成物，已开场会话使用绑定的求时器。
- **事件日志与摘要。** 每个处理的事件折叠进 `digest`，事件码表在 `paid/events.ts`，TS 与 Solidity 逐项一致，向量逐字段比较摘要。

同毫秒内的事件按类处理，类内按括号中的键升序，同毫秒新产生的项按同一规则继续插入：

```
积分推进到最早事件（无场解析 / 有场 RK2 定点积分，步长 ≤ 250 ms）
     → 0 效果到期与移除（instanceId）
     → 1 基础速度封顶、体力见底与回满（horseId，同一匹马先封顶后体力）
     → 2 冲线（horseId）→ 3 炸弹首次触线，死亡或免死（horseId，炸弹序号）
     → 4 周期与监听触发：交换尝试、风火轮爆发、C-23、C-24、C-40（instanceId）
     → 5 里程检查点越过：电脑马取卡，玩家开面板、断卡或推迟（horseId）
     → 6 玩家面板关闭与取卡
     → 该毫秒无新事件，建立下一积分区间
```

三条不能挪的顺序：

- **炸弹用连续轨迹的首次触线定位。** 不能只在事件端点检查坐标相等，否则高速运动会漏判。
- **重力井在积分内部计算。** 以该时刻真实距离给当前基础速度提供百分比贡献，不能把场视作单次触发事件或改基础上限。
- **里程只累加自身运动积分。** 位置跳变后用新 `pos` 判断终点，但交换位移不计入 `dist`。

跨语言向量 `tests/vectors/paid-race-v0.1.json`（360 组，由 `scripts/gen-paid-vectors.ts` 生成，`tests/contracts/PaidRaceSolverVectors.t.sol` 在 Solidity 复算）逐字段比较事件、摘要、检查点、冲线时间与结算排序；`gen-paid-card-rules.ts --check` 与 `gen-paid-vectors.ts --check` 校验生成物没有过期。

## 6. 表现层：插槽与资源

[卡牌设计 §9](../card-design.md) 要求装备挂到马的不同部位。渲染职责划分如下：

```text
src/race/paidSnapshot.ts  求时器轨迹 → RaceState 与 RaceEvent，表现层读取的唯一规则快照
src/race/driver.ts        免费试玩驱动器：本地时钟与本地入场锚
src/race/paidDriver.ts    有奖驱动器：链上规范时间线
src/game/RaceScene.ts     赛道、环境、一次性事件、镜头与 Phaser 场景时序
src/game/pony.ts          PonySprite：马体动画、状态、装备与头饰挂点
src/game/effects.ts       支持的装备/天气素材、状态筛选与纯几何表现数据
src/game/gogoCamera.ts    gogo 点击密度到镜头构图偏移
src/game/sceneArt.ts      按资产 key 解码赛道与效果图片
src/ui/race/raceEventAudio.ts  RaceEvent 到音效与冲线旋律的映射
src/ui/race/RaceScreen.tsx     驱动器帧更新与 HUD 浮层
```

**表现层读取快照，规则层不知道表现层存在。** `paidSnapshot.ts` 把求时器轨迹按固定比例换成 `RaceState`（其中的 `EffectInstance` 带 `primitive` 与 `tags`，只供 HUD 与场景筛选）和 `RaceEvent`，不做任何速度、体力或名次计算。`RaceScene` 把赛道、环境和一次性事件分层绘制；`PonySprite` 负责马匹动画、状态和装备；`sceneArt.ts` 根据资产 key 解码背景与特效图。表现层按帧读取当前 `RaceState` 中的装备实例，所以转移后的装备跟随新持有者；`RaceEvent` 只用于需要播放一次的转移动画、声音、碰撞反馈或 `cardEffect` 浮字（触发、资源增减、固定值、目标、拦截、翻新）。规则层不导入 Phaser、音频或图片资源。

gogo 只喂 `GogoCameraMotion`（点击密度到构图偏移），`RaceScene` 以同一镜头位置绘制全部世界对象；玩家默认在画面左起三分之一处，连续点击最多推到三分之二，不进入规则状态与求解输入。

开发验收入口使用完整40张 `PAID_CARD_POOL`，通过生产 `solvePaidCore`、轨迹采样和 `buildPaidSnapshot` 展示规则行为，并复用生产RaceScene/PonySprite。独立入口只负责确定性输入与模拟时钟，不维护第二套效果数值；不调用钱包或合约，生产构建不显示入口。

C-09 的成功 `swap` 事件播放 `audio.sfx_swap`，不触发专属镜头、闪光或交换粒子；两匹马直接按新位置绘制。C-10 的 `Field` 不显示范围与目标反馈，来源只由持有者身上的黑洞装备表达。C-11 的【火焰】层数不渲染到马身，身体只显示四蹄风火轮与已有的【起飞】姿态。

C-02 的【运气E】状态由免费试玩与有奖比赛共享的 `paidSnapshot.ts` 在 `speedDeath` 实例上输出 `Status`、`statusId: 'luckE'` 与 `spin: true`，保留 `buff`、`debuff` 标签和原实例期限，不新增实例或事件。状态驱动马体围绕马图垂直中心纵向压缩/翻面，并叠一条居中于马图中心的螺旋拖尾突进分镜（16 帧、650 ms 循环），不随马体翻面；该表现不回写规则。C-07 火箭和 C-10 黑洞挂在躯干腹部，作为 `PonySprite` 根节点的子对象，随【起飞】升降。C-13 消费 `steal { from, to, equipId }` 事件，在装备实际变更的两匹马挂点间播放同一装备素材的短弧线转移；场景快照仍决定最终挂载，事件只驱动过渡演出。C-19、C-20 的毛色显示为头顶尖发：`activeHeadCosmetic` 按最近一次染色卡选金色或绿色素材，挂在头部锚点并随根节点升降与翻面，不改马体贴图。选中马的金圈由 `RaceScene` 独立绘制在马匹深度之下。减少动态效果时 C-02 保持稳定姿态，C-13 直接完成转移，不影响规则状态。

### 6.1 开发特效验收入口

首页开发入口进入独立验收场景。场景驱动器提供固定种子、马匹/赛道布局、模拟时间和预设状态，不伪造规则结果，也不改变求时器。验收入口复用 `RaceScene` 的资源、坐标、缩放与挂载逻辑，因此能检查实际游戏视口里的尺寸、遮挡、层级和转移位置；生产对局继续由 `RaceDriver`/`PaidRaceDriver` 驱动。

入口列出完整40张 PAID_CARD_POOL，以生产求时器实际卡牌、状态、事件与生命周期显示。场景可暂停、逐步推进、重播和切换；风火轮层数与黑洞范围不增加马身特效。

首页入口只由 import.meta.env.DEV 控制；验收情景不提交链上选择、不写钱包或持久化比赛。规则来自实际求时器，展示时钟按页面单调相对时间推进，不用Date.now或Math.random决定规则事件。

验收以源码测试和确定性场景检查为门槛：测试覆盖情景状态、效果映射、装备转移事件与 reduced-motion 分支；浏览器验收再核对真实 `RaceScene` 的动画、挂点、层级和首页入口的开发/生产可见性。短片用于评审时序与风格，不能代替状态、生命周期和资源映射测试。

`laneIndex` 是规则层的可变站位，交换时与 `pos` 一起置换；渲染层读取它决定马画在哪一行。C-09 在自身之外四个 `laneIndex` 中抽目标；除此以外，`laneIndex` 不得影响速度、里程或名次判定。

资源缺失一律降级为占位，不阻断规则（[卡牌设计 §9.2](../card-design.md)）。**规则层不 import 任何资源清单**，这是美术进度与数值调参解耦的唯一方式。

## 7. 目录结构

在[架构 §3](overall.md) 的基础上细化 `src/race/`：

```text
src/race/paid/        求时器：规则表、求解、运动学、事件码与摘要、渲染轨迹、入场派生、体力资源
src/race/core/        入场派生与结算的纯函数（性格、牌堆、发牌、交换、名次）、定点数、RNG，以及表现层使用的 RaceState 类型
src/race/cards/       卡面：元数据（名称、梗源、图标）、由规则表生成的说明、完整40张由规则表生成的生产卡面与兼容导出
src/race/*.ts         驱动器与快照：driver.ts（免费试玩）、paidDriver.ts（有奖）、paidSnapshot.ts、paidResult.ts、paidWindow.ts、raceView.ts
contracts/Paid*.sol   求时器的 Solidity 复算；PaidCardRules.sol 由 cardRules.ts 生成
tests/vectors/        跨语言向量 paid-race-v0.1.json、构筑分析 paid-card-builds.json
```

规则表是纯数据：**加一张已有机制的卡，正常路径是往 `src/race/paid/cardRules.ts` 与 `src/race/cards/metadata.ts` 各加一条记录，不改求时器一行。** 如果一张新卡逼着你改求时器，按 §4.1 走完整流程。
