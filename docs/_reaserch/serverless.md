# 无服务端方案探索

## 探索原因

这个 demo 的首要目标是让游戏动起来、真正好玩。这不只是优先级排序，它直接决定信任边界划在哪里，因为下面三件事互相排斥：

1. **要让合约校验名次，玩法就必须是确定性的、开场即可枚举的。** 校验的前提是合约能独立算出「这个结果是否可能」，而这要求整场的每个变量在起跑那一刻就已确定。
2. **开场就确定的比赛没有游戏性。** 若四匹电脑马的成绩在下注瞬间已定死，玩家做的只是在一个已知区间里挪动自己的落点，结局在按下开始之前就写完了。
3. **防作弊是反游戏性的。** 每一条防御最终都是对玩家输入的约束：输入条目上限、节奏影响上界、卡牌不得作用于对手。这些约束不为玩法服务，只为校验服务。

「链上可校验」与「过程不确定」因此不是两个可以分别优化的指标，而是同一根轴的两端，必须选一端。本 demo 选不确定那一端：**游戏从开始时固定的只有卡牌组合，中间的进行时不固定，最终的位次以浏览器的运行状态为准。** 与之配套的第二条判断：平衡是随玩法调整持续移动的目标，把赔付表与防御阈值焊进合约等于把动态量固化成部署产物，每次调手感都要重新部署并迁移资金。

真正要回答的问题因此不是「无服务端是否可行」，而是**信任边界划在哪里**——让浏览器自由地跑一场不确定的比赛，同时让链上仍持有一份别人拿得走、算得清的记录。

## 探索目标

1. 划定 demo 阶段的信任边界：哪些事实必须由链持有，哪些明确交给浏览器。
2. 确定 seed 的唯一职责，以及「发牌可验证」的实际含义与它不能声称的部分。
3. 确定合约保持玩法无知时，将来要加校验需要什么样的接口，才能不重新部署、不迁移资金。
4. 保留将来动手做链上校验时的现成依据（成本量级与链的事实），当前不展开论证。

## 探索结果

结论：合约只管钱和记录，名次以浏览器为准；seed 只固定发牌；电脑马是实时橡皮筋 AI；校验能力以可替换钩子的形式预留，demo 期指向 `AlwaysAccept`。其中最有决策价值的一条在第 3 节——**「暂时不校验」比「先做一个弱校验」更容易升级**：弱校验也是玩法断言，一旦写进主合约就永久烧死在部署产物里；而玩法无知的主合约配一个可替换的校验器，整条升级路径都不必触碰资金。

### 1. demo 阶段做什么

合约只有两个入口，都对玩法无知。`enterRace`：收下注进 Vault，在本笔交易内派生并存储 `seed`，记录本场 `rulesVersion`。`settleRace`：接受浏览器报告的名次与完整比赛记录，过一遍 `IResultValidator`，按赔付表发钱，发一条只带检索字段的 event。

它不派生电脑马、不校验完成时间、不重放、不解析记录内容。它守住的是账本——谁下了多少、赔付表是什么、这场记录是什么——而不是玩法结果。

#### 1.1 seed 的唯一职责是固定发牌

seed 决定一副 **14 张互不重复的有序牌堆**，三个检查点按游标各取三张，余量供刷新（完整式子见[玩法设计第 4 节](../game-design.md)），除此之外不承担任何职责。抽取顺序是派生式的一部分，无放回使第 k 张取决于前 k−1 张抽走了谁。合约不需要知道发了哪几张，只需要保证 seed 不由玩家挑选。**seed 只固定「给了什么」，不固定「用了什么」和「跑成什么」。**

可验证性的含义必须说准确：任何人能用链上 seed 重算出那副牌堆并与前端展示比对，因此运营方无法为特定玩家定向发牌；但它不阻止玩家不按发牌玩，也不对名次构成任何保证。这是一份可复核的发牌记录，不是防御，对外文案不得写成后者。顺带的收益是合约钱包虽仍可在入场交易内读 seed 并条件 revert 重 roll，收益却只剩换一手更合意的构筑——这条在确定性模型里是必须堵的口子，在当前模型里降级为可忽略项。

#### 1.2 电脑马是实时橡皮筋 AI

四匹电脑马每帧按与玩家的相对位置调速：领先过多收油，落后过多追赶，各自带不同的性格参数（`base/min/max/gain/slack/ease` 六个数，由 seed 派生）。它们没有预设成绩，也没有目标名次。**严禁以名次或目标完成时间作为速度依据**——一旦出现「这匹马要拿第三，所以现在该跑多快」，就回到了先定结局再编演出。

代价必须写明：橡皮筋 AI 的速度依赖玩家每一帧的位置，没有闭式解，也不能由 seed 派生。**选择橡皮筋 AI 就等于选择了名次不可被链上独立算出。** 这不是当前偷懒、将来补上的事，是这一整类 AI 的性质；将来若要链上校验，必须连同 AI 一起换掉（见 3）。

手感目标是两个可测的数：同一场里最优玩法与放任不管的名次差期望 2–3 名，「怎么打都一样」的局低于 5%。它们是调橡皮筋参数达成的指标，不是任何公式的输出，同时也是橡皮筋强度的上界约束——拉得越紧，玩得好与玩得烂的名次差越小，两者是同一个旋钮的两端。

#### 1.3 结算 calldata 就是比赛记录本身

`settleRace` 的 calldata 承载完整的一场记录：名次、玩家选的 `horseId`、完成时间、三次选牌、刷新位置、有效点击序列、结束原因与 `rulesVersion`。`horseId` 决定四组电脑马参数怎么分配，少了它整场重放不出来；赛道不进记录，它只是画在第几行。合约不解析它，只校验长度在上限内（长度决定 gas，必须有界）。event 只带检索需要的字段（`Entered(raceId, player, stake, seed, rulesVersion)`、`Settled(player, rank, payout, rulesVersion)`），完整内容从 calldata 取。

**不要只存哈希。** 哈希的可审计性在这里是零——链上没有第二份数据可比对，它只能证明「提交者当时知道一份数据」，不能让任何人拿到它。calldata 本身永久可读，多付的只是每非零字节 16 gas。真正能被第三方拿走复核的记录是这份原文。

### 2. 明确不做什么

以下都是取舍不是遗漏，写进文档是为了让将来的人不必重新论证。

| 不做 | 理由 |
| --- | --- |
| 完成时间区间校验 | 它是玩法断言，会永久烧进主合约，反而堵死 3 的升级路径 |
| 由 seed 派生电脑马成绩 | 那要求开场定死结局，与本文的核心判断直接冲突 |
| 链上重放 | 需要规则的第二份实现与确定性玩法，两项前提当前都不成立 |
| seed 重 roll 防御 | seed 只决定发牌，重 roll 收益是换一手构筑，不值一个 EIP-2935 依赖 |
| 可验证公平随机（VRF） | 引入等待时间、费用与中止偏置，换来的性质当前无人消费 |
| 防出块者操纵 | 攻击成本是出块权，收益受单笔最大下注限制 |
| 赔付表按最优策略定价 | 测试网 MON 无价值，被抽干的代价是重新注资，属运维问题 |

由此，两条表述纪律不得违反：「无需信任运营方」当前只意味着运营方无法指定结果与定向发牌，不意味着结果不可伪造；seed 是运营方无法指定的随机，不等于可验证公平随机。

### 3. 将来怎么加，且不需要重新部署

四件事从第一天就做，使升级不必触碰主合约与资金：**主合约对玩法无知**、**`rulesVersion` 随场记录**、**赔付表可配置而非硬编码**、**结果校验走一个可替换的钩子**。

```solidity
interface IResultValidator {
    function validate(address player, bytes32 seed, uint32 rulesVersion,
                      uint128 stake, uint8 rank, bytes calldata inputLog)
        external returns (bool);        // 刻意不是 view
}
```

主合约只调用它、只看返回的 bool。demo 期指向 `AlwaysAccept`（恒 true，几乎零 gas）。

**接口刻意不声明为 `view`。** `view` 能换来「校验器改不了状态」这个静态保证，但同时堵死了一切需要写状态的校验——争议记录、罚没、分批校验、跨场累积统计。这个钩子存在的唯一理由就是避免重新部署主合约，用一个现在看不出代价的签名限制换掉一半升级空间，与它自己的目的相悖。`AlwaysAccept` 的实现仍可声明为 `pure`，Solidity 允许实现比接口更严格。

资金安全因此不靠 `view` 保证，靠三条边界：**校验器从不持有资金**，转账始终由主合约在校验返回之后自己执行；**`settleRace` 按「检查 → 改状态 → 外部调用」执行并加 `nonReentrant`**，校验器被调用时待结算记录已删除、`reserved` 已释放，重入拿不到任何未清理的状态，最坏情况是它误拒、结算失败、下注留在 Vault，与弃赛同一路径；**主合约与 Vault 地址不变**，升级只是一次 `setValidator` 的治理调用，资金不移动，玩家不换地址，战绩不断档。

主合约只持有**一个**校验器地址，不做按 `rulesVersion` 的分派——`rulesVersion` 随每场记录传进 `validate`，要分版本处理是校验器自己的事。分派表放进主合约就又是一处会变的状态，与「主合约里没有会变的东西」直接冲突。

关键在于主合约里一行玩法断言都不能有。哪怕只是一次 `finishTick` 的区间比较，那条断言也会永久留在部署产物里，将来要改只能重新部署并迁移资金。要补付的工程量则免不掉：链上校验需要规则的 Solidity 第二份实现与跨语言位级一致性向量（同一组 `(seed, 输入序列)` 下终态逐字段相等，不接受容差），并且要求玩法先退回确定性模型——橡皮筋 AI 必须换成可由 seed 派生的对手。接口只免掉重新部署与资金迁移这一块。

### 4. 将来动手时的现成依据

**重放的 gas 量级（按 EVM 操作计价推算，非实测）：** 玩家一匹马，50Hz × 90 秒 = 4500 步，每步约 20–30 个整数运算，保守取 250 gas/tick，重放约 1.13M，整笔约 1.2M。单笔上限 30M，占约 4%，gas 不是阻碍。若电脑马也要重放则乘 8，约 9.6M——仍在上限内但不再宽裕，这是「链上校验必须先换掉橡皮筋 AI」在成本侧的第二个理由。

**Monad 事实**（2026-09-12 查阅官方文档；事实为查阅所得，上面的 gas 数字为推算）：

| 事实 | 值 | 意义 |
| --- | --- | --- |
| 单笔 / 区块 gas 上限 | 30M / 150M | 重放的 1.2M 量级不构成约束 |
| 计费方式 | 按 gas limit 扣费，不按实际消耗 | 当前结算成本只随 calldata 长度线性变化，封存输入时即可精确估算；若将来改为重放，成本随点击数浮动，必须逐场估算 |
| 出块间隔与终局 | 300ms，两块终局约 600ms | 决定入场确认等待，可与起跑倒计时重合 |
| `BLOCKHASH` 窗口 | 256 块，约 76.8 秒 | 短于一场比赛，延迟派生不能单独依赖它 |
| EIP-2935 | 已启用，可回溯 8191 块，约 40.9 分钟 | 若将来需要延迟一块派生 seed，它提供足够窗口，代价是同长度的结算窗口 |
| `block.prevrandao` | 官方未说明 MonadBFT 下的返回值 | 任何阶段都不能作为唯一随机源；留在派生式里是零成本冗余 |
| 官方推荐随机源 | Pyth Entropy、Supra dVRF、Switchboard | 均为第三方服务，引入即引入等待时间、费用与中止偏置 |

## 注意事项与补充

- 本文的取舍前提是**测试网、资产无价值**。它不随部署环境自动沿用；主网化前必须重走第 3 节，且那时要动的是玩法模型本身，不只是加一层校验。
- 名次由浏览器报告，因此链上记录是**可复核、不可阻止**：第三方能取出 calldata 与 seed 发现「这份输入跑不出这个名次」，但合约不会因此拒付。战绩页可据此标注，不需要改合约。把它写成一致性保证是错的。
- 合约读不到自身交易的 txHash，入场与结算的关联靠共享的 `raceId`：两笔交易各发一条带 `raceId` 索引的 event，审计者据此配对。
- Vault 偿付的最小做法是限制单笔最大下注，并在 `enterRace` 时要求余额足以覆盖最大赔付，并维护一个 `reserved` 累加器（不是逐场预留账本），覆盖弃赛记录时释放旧场那一份。偿付不足是可用性约束，不是资金安全约束。
- 若将来引入玩家之间的对抗或撮合，「作弊只损害 Vault」立即失效，另一个玩家成为受害者，整套取舍需要重新探索而不是打补丁。
