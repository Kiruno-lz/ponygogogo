# 技术架构

## 1. 总体决策

静态 Web 前端负责输入、画面和可复算的本地预览；Monad 上的 `PonyGame` 以冻结规则、链上选择与区块哈希独立计算五匹马排名，`PonyVault` 只接受其结算指令。当前仓库仍运行浏览器 mock，链上复算是待交付目标。

## 2. 技术与数据流

Vite、React、Phaser 负责页面和赛道；TypeScript 纯规则内核做浏览器模拟与测试向量；Solidity/Foundry 实现权威规则复算。Mera 根 EOA 恢复独立 Alchemy `sma-b` 智能账户；该账户持有固定 ERC-20，在开场、检查点选择、随机锚封存和结算时签交易。两套规则实现必须使用同一版本、定点整数、事件优先级和舍入规范；TypeScript 输出不是合约可信证明。

```text
链上入场 seed/规则/赔率 → 浏览器五马预览
        ↓
三次可能的选择交易 → 后续区块确认各选择块哈希
        ↓
浏览器冲线展示待验证名次 → PonyGame 复算 → PonyVault 返还
                                                 ↓
                                              Envio 查询
```

## 3. 规则模块

`src/race/core/` 管五马事件求时、体力—加速度、无场解析积分、有重力井时的定点数值积分、冲线时间和物理/结算两层名次；`src/race/cpu/` 只提供入场时冻结的电脑马基础参数，不逐 tick 求目标速度或噪声；`src/race/modules/` 管卡牌、状态、Hazard 和 Field；`src/game/` 只采样轨迹渲染、音效与同一水平摄像机。合约实现同一冻结规则。跨马卡牌可以明示改变目标马状态，但 CPU 自主运动不能读取玩家位置、名次或镜头。

gogo 点击只计算表现层镜头偏移：高频向左移、低频向右回归，玩家马始终在屏内。所有马应用同一个镜头变换，彼此的屏幕相对位移只取决于规则位置。gogo 不进入规则内核、体力、卡牌触发、随机计数器和链上交易。体力按模拟时间独立消耗/恢复。

## 4. 确定性与随机

seed 与入场区块 `b_0` 的哈希共同确定初始牌堆和五马基础参数。实际选择/主动放弃的交易同时锁定秒级入块时间 `Ti` 与区块号 `b_i`；自动选牌只用先前锁定的锚，超时与断卡不产生新随机锚；各锚在后续块由 `blockhash(b_i)` 验证，随机事件使用 `H(seed, blockhash(b_i), i, purpose, eventIndex)`。自动抽牌、交换、风向、窃取和重复触发各自域分离。未确认哈希不能永久写入规则状态；过可读窗口前必须链上封存。第三个实际检查点处理完且已使用的锚可读后不再新增随机源，可预计算冲线结果，画面仍等玩家实际冲线才展示。

输入日志包括选择、刷新、放弃、超时和规则事件，不包括 gogo 镜头点击。规则时间按真实经过时间推进，选牌期间降到 0.1 倍；合约从入场时间 `T0` 与选择时间 `Ti` 建立事件区间并直接求五马冲线时间。百分比效果乘当前基础速度，固定值加在乘法之外；重力井按实时距离变化并由冻结积分算法求解。浏览器本地时钟只绘制待确认画面，交易入块后按链上规范时间线重新求时。浏览器及 Solidity 的事件状态、量化冲线时间、`rawRank` 和 `settlementRank` 必须逐字段一致，不接受未经规则定义的浮点容差。无效、缺失或过期输入由冻结规则处理，不由本地时间补填。

## 5. 比赛生命周期

开场锁定资产和赔付能力，冻结规则版本、seed、卡集合与入场时间；各检查点按里程触发候选，选择交易锁定结果、入块时间及区块号；后续区块封存哈希；玩家冲线时展示待链上确认的预览；`settleSession` 复算并支付。早于第三检查点冲线的比赛仅包含实际发生的检查点。过期会话显式退款，结算与退款互斥。网络中断后从合约状态、调用 ID 和交易哈希恢复，不以浏览器快照决定奖金。

## 8. 卡面与结算展示

卡面只有一套实现，在 `src/cards/`。选牌时的候选牌、HUD 上生效中的牌、结算页回顾的牌是同一个组件的三种状态，不是三套画法——两套画法迟早在品质配色、数值排版或图标上跑偏，而这三处恰好是玩家在一局里反复对照的地方。

**卡牌在 DOM 层，不在 Phaser 里。** 卡面是文字、数值与品质样式的排版，DOM 在这件事上便宜得多，响应式与可访问性也是现成的；Phaser 画同样的东西要自己管字体度量和换行。代价是浮层与画布要在 z 轴上正确叠放，且选牌浮层出现时赛道继续跑——卡牌层绝不暂停 Phaser 场景。

三段动画都归这个模块：发牌入场（三张错峰落位）、悬浮（指针与键盘焦点共用同一视觉态）、选定消失（选中的一张飞向 HUD 对应槽位，另两张淡出）。

**硬约束：动画不参与规则。** 选牌效果按交易入块秒级时间映射的规范模拟时刻生效，区块哈希在后续块验证；飞行与淡出只是表现。gogo 点击只写镜头状态，不写比赛输入序列。动画时长不进入求时器；掉帧、`prefers-reduced-motion` 或直接关掉动画都不得改变名次。

组件动效统一由表现层状态差异驱动：按钮按下播放缩放，`gogo` 额外播放旋转与缩放，状态新增或层数增加播放图标/层数徽章的缩放与摇晃。规则层只提供已经提交的状态快照或表现事件，不直接操作 DOM/Phaser 对象；表现层不得把动画完成、取消或掉帧回写为规则输入。动画连续触发时只保留最新一次，不建立等待队列。

选牌的 20 秒现实限时**从规范模拟首次跨过检查点的时间起算**；卡面出现即允许操作，入场动画不得占用可操作时间，浏览器显示的倒计时须按链上规范时间校正。慢设备不能靠延长本地动画顺延链上截止时刻。

首页与结算页的美术走同一套方法：木牌、按钮、标题这类素材由作者直接出成**无字透明图**，文字在 DOM 里排版覆盖上去——换语言只换文本节点，不换图，不必为每种语言维护第二套切片。版位不靠自动流式布局，而是把新素材的实体包围盒（排除投影一类中性灰区域）对到原画参考图（`art-src/renders/tittle.png`、`art-src/renders/result.png`）里同一块牌的包围盒，横纵缩放各自换算——素材未必是原生尺寸，允许按版位比例小幅拉伸。两屏各自对齐自己那张原画的画布（首页 1611×976、结算页 1620×971），`src/App.tsx` 按当前页面选用对应画布尺寸，与赛道渲染画布互不影响。悬浮反馈必须走 `filter`（`brightness` 叠 `drop-shadow`），不能用 `background`/`box-shadow`：前者只对切片里有 alpha 的像素起效，后者会把切片外那圈透明矩形一起提亮，糊成比按钮本身大一圈的方块。

`src/result/` 负责冲线之后的那一屏：名次、总返还、净盈亏、本场三张牌的回顾，卡面复用 `src/cards/`。名次徽记拆成两层——木牌+名次条的 `nameplate.png` 在下，按名次取图的奖章 `medal-1..5.png` 在上，与原画里奖章压在木牌之上的顺序等价；名次数字画在奖章牌面上，DOM 里不再叠数字，只留一个供读屏与测试取值的隐藏节点。它在冲线封存后立即可显示，**先标记为待验证预览，不等链上确认才展示画面**——奖金结果由 PonyGame 独立复算（第 1 节），资金状态是另一条独立的进度，按[链上文档第 4 节](../chain-and-economy.md)的 `Preparing / Submitted / Included / Finalized` 单独标注。两者不得合并成一个"结算中"转圈，否则玩家会以为名次还没定。

## 9. 出图与分享

`src/export/` 只做一件事：把一场比赛变成一张 PNG，再交给平台。

**海报用离屏 Canvas 自己画，不截屏 DOM。** 把结算页光栅化（html2canvas 一类）在字体加载时序、跨域图片与 CSS 支持面上都不可靠，而海报的内容本来就是固定版式：名次、三张牌、成绩、seed 前若干位与结算 txHash。自己画一遍是确定的，截屏是碰运气的。

三条分发路径的实际能力不一样，接口按能力划分而不是按平台命名：

| 能力 | 实现 | 真实约束 |
| --- | --- | --- |
| `toBlob()` | 离屏 Canvas | 无 |
| `copyToClipboard()` | `navigator.clipboard.write([new ClipboardItem({'image/png': blob})])` | 必须在用户手势的同一个任务内。Safari 下要把 Promise 直接交给 `ClipboardItem`，不能 `await` 之后再构造，否则手势上下文已失效 |
| `share()` | `navigator.share({ files })`，不可用时降级为下载 | 桌面端普遍不支持带文件分享 |

按平台说清楚能做到什么，不要在 UI 上承诺做不到的事：

- **X**：web intent（`https://x.com/intent/post?text=…&url=…`）**只能带文字和链接，不能带图片**。静态前端没有服务端，也就没法给每一场生成带 OG 图的独立 URL。因此实际动线是「先写剪贴板 → 再开 intent → 提示玩家粘贴」，按钮文案必须说明这一步，不能做成一键直发的样子。
- **Instagram**：web 端不存在分享 API。唯一可行路径是移动端的 `navigator.share({ files })` 唤起系统分享面板，玩家在面板里选 Instagram；桌面端只能下载图片后自行发布。

因此 `share()` 先用 `navigator.canShare({ files })` 探测再分流，模块对外不暴露 `shareToInstagram()` 这种按平台命名的方法——那会让调用方以为存在一条直达链路。
