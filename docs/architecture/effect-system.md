# 效果系统与模块化架构

[总体架构](overall.md)把 `src/race/` 定为唯一一份规则实现。本文在其内部划一条界：**骨架与模块。** 卡牌设计在[卡牌与效果系统设计](../card-design.md)，本文只定模块边界、扩展点与确定性约束。

## 1. 为什么要切这一刀

卡牌是本作的核心玩法，卡池会长期增长，而[卡牌设计 §3](../card-design.md) 的九类原语里有六类要写入马匹自身属性之外的东西：场上实体、区域场、全局环境、跨马转移、输入绑定、发牌游标。如果这些直接长在推进循环里，`src/race/` 会在第 30 张卡之前变成一个谁都不敢改的函数——每加一个效果都要往 tick 循环里插一段，而每一段都可能改变已有卡牌的结果。

因此骨架只负责**所有马都要做的事**，一切「某些卡才会发生的事」进模块。判据不是「代码量大不大」，是**这段逻辑在卡池为空时还需不需要存在**：需要就是骨架，不需要就是模块。

## 2. 骨架：`src/race/core/`

骨架在卡池为空时必须能独立跑完一整场五匹马的比赛。它包含且只包含：

| 职责 | 说明 |
| --- | --- |
| tick 循环与处理顺序 | 固定步长、固定阶段顺序，见 §5 |
| 马匹运动学 | 加速度 → 积分 → 钳到速度带 → 位移与里程，玩家与电脑马共用；加速度的来源两边不同（[架构 §6](overall.md)） |
| 体力 | 消耗与恢复的基础模型 |
| 里程与终点 | `dist` 累加、里程档触发、`pos ≥ L` 的冲线与名次判定、`forcedRank` 分支 |
| 资源模型 | 体力的消耗、恢复、上下限与 **overcap**（超上限部分只减不增） |
| 确定性 RNG | 域分离派生，唯一随机源 |
| 效果实例容器 | `EffectInstance` 的挂载、计时、到期移除 |
| 乘区聚合 | B1–B4 与体力两区的收集与结算 |
| 模块调度与事件队列 | 按固定顺序调用模块钩子，见 §4 |

**效果容器与乘区聚合归骨架，不归模块。** 它们是全部模块共用的基础设施；放进模块会让两个模块各自实现一遍计时，然后在某个边界 tick 上不一致。

**里程也归骨架**，即使卡池为空它仍然要算——检查点抽卡是玩法骨干，不是某张卡的效果。

橡皮筋 AI 仍在 `src/race/cpu/`，同样是骨架的一部分而不是模块：没有它就没有对手，比赛不成立。

## 3. 模块：`src/race/modules/`

一个模块声明自己要读什么、写什么、挂哪些钩子：

```ts
interface RaceModule {
  id: string                 // 稳定字符串，决定同 tick 内的执行顺序
  version: number            // 参与 rulesVersion 计算
  reads: ReadScope[]         // 静态可检
  writes: WriteScope[]       // 静态可检
  hooks: Partial<ModuleHooks>
}
```

当前卡池对应的模块清单：

| 模块 id | 职责 | 对应卡牌 |
| --- | --- | --- |
| `mod.speed` | B1 卡牌速度增益区 | 全部加速卡 |
| `mod.stamina` | 体力经济修正 | 火箭喷射器 |
| `mod.airborne` | 【起飞】状态与 `Hazard` 免疫 | 中国马能飞、风火轮 |
| `mod.death` | 【死亡】【重生】结算 | 旋转突进、炸弹来咯、风火轮 |
| `mod.stack` | 层数状态（【火焰】） | 风火轮 |
| `mod.equipment` | 装备挂载与插槽绑定 | 火箭喷射器、彩虹猫、重力井、风火轮 |
| `mod.ability-bind` | gogo 按钮的单槽绑定与占用期间的节奏折半 | 不义游戏、风火轮 |
| `mod.swap` | 两匹马的 `pos` / `laneIndex` 置换与冷却 | 不义游戏 |
| `mod.hazard` | 场上实体的放置与区间触发 | 炸弹来咯 |
| `mod.field` | 区域场的距离衰减与目标收集 | 重力井 |
| `mod.draw` | 牌堆游标：刷新、自动抽取、断卡 | 海贼王的宝藏、选择困难综合症、最后的波纹 |
| `mod.env` | 全局环境单槽：写入、替换、按 `gate` 分发到受影响的马 | 起风了 |
| `mod.steal` | 跨马装备转移：查询、摘除、重挂、时长刷新 | 顺手牵羊 |
| `mod.trigger` | 条件触发器：到期、层数阈值、资源阈值 | C-02、C-11、C-16 |
| `mod.cosmetic` | 外观状态与表现层剥夺（毛色、视野） | 黄毛、染成绿的、理解孙学 |
| `mod.suppress` | 按 tag 抑制/移除效果实例，含系统自持的力竭惩罚 | 咖啡因过量 |
| `mod.combo` | 持有集合匹配与彩蛋结算 | 版本答案 |
| `mod.trail` | 拖尾（**纯表现，零规则写入**） | 彩虹猫、旋转突进 |

`mod.swap` 同时置换两匹马的 `pos` 与 `laneIndex`：`horseId` 仍是身份，`laneIndex` 是可变的上下站位，渲染层按它画在第几行（[玩法设计 §2](../game-design.md)）。速度、里程和同 tick 冲线兜底排序不读取 `laneIndex`。

`mod.trail` 列在这里是为了让「这张卡需要什么」在一处看全；它注册的钩子只读不写，静态检查会强制这一点。

[卡牌定义](../card-design.md)的 `modules` 字段列出该卡依赖的模块 id。**缺模块时在构建期失败，不在运行期静默无效**——一张卡的效果悄悄不生效，是这类数据驱动设计最难查的 bug。

## 4. 扩展点与写权限

### 4.1 钩子

```ts
interface ModuleHooks {
  onEffectApply(ctx, inst): void          // 效果实例挂载，瞬时动作在这里执行
  onEffectRemove(ctx, inst): void         // 被移除（转移、插槽覆盖、单槽替换），区别于到期
  onEffectExpire(ctx, inst): void         // 到期，【运气E】的死亡结算在这里
  contributeSpeed(ctx, horse): Buckets    // 只返回乘区贡献，不直接写速度
  contributeStamina(ctx, horse): Buckets
  onInputIntent(ctx, intent): void        // gogo 按钮的语义由当前绑定解释
  onPositionJump(ctx, horse, from, to): void  // 交换等瞬时置换
  onMileageMark(ctx, horse, markIndex): void  // 里程跨过 0.25L / 0.50L / 0.75L
  onDrawRequest(ctx, req): DrawRequest    // 修改牌堆游标行为
  onHorseFinish(ctx, horse): void
}
```

`contributeSpeed` 返回的是**分算子、分阶段的贡献**（`add` / `padd` 按池 / `mul`），不是一个数；骨架按[卡牌设计 §3.2](../card-design.md) 的固定阶段顺序聚合。模块不自己决定落在哪一阶段，声明里写什么算子就落在哪一阶段——否则两个模块会对「我该乘还是该加」各有一套理解。

`contributeSpeed` **返回**贡献而不是写入速度，这是刻意的：返回值可以被骨架按固定顺序求和，写入则依赖调用次序，而调用次序是最容易在重构中悄悄改变的东西。

### 4.2 写权限矩阵

这张表是[玩法设计 §6](../game-design.md) 那条硬约束的架构落点。模块只能通过骨架提供的 `MutationAPI` 写，`writes` 声明之外的写入在类型层面不可达：

| 写入对象 | 允许的模块 | 禁止 |
| --- | --- | --- |
| 玩家马的乘区贡献 | 任意模块 | —— |
| 任意马的当前速度、`pos` | `mod.death` `mod.swap` `mod.hazard` | 其余模块 |
| 任意马的 `laneIndex` | `mod.swap` | 其余模块 |
| 任意马的外部速度乘子 `field_i` | `mod.field` `mod.env` | 其余模块 |
| 任意马身上的装备实例（摘除与重挂） | `mod.steal` `mod.equipment` | 其余模块 |
| 全局环境槽 | `mod.env` | 其余模块 |
| `forcedRank`（强制名次） | `mod.combo` | 其余模块；这是名次唯一不由位置推出的入口 |
| 按 tag 移除效果实例 | `mod.suppress` `mod.steal` | 其余模块 |
| 电脑马的 `base/min/max/gain/slack/ease/amp/tau` | **无** | 全部模块，无例外 |
| 电脑马目标速度函数的入参集合 | **无** | 全部模块，无例外 |
| 任何马的 `dist` | **无** | 全部模块；里程只由骨架按自身位移累加 |
| 渲染层状态（毛色、可见性） | `mod.cosmetic` **只写状态标记** | 任何模块直接操作渲染对象 |
| 牌堆游标 | `mod.draw` | 其余模块 |
| 场上实体 | `mod.hazard` | 其余模块 |
| 输入绑定槽 | `mod.ability-bind` | 其余模块 |
| 渲染层状态 | **无** | 规则内核单向依赖，不得反向写渲染 |

**跨马写入是双向的**（[卡牌设计 §2.1](../card-design.md)）：玩家的卡能写电脑马，电脑马的卡也能写玩家，因此上表前四行都写「任意马」而不是「电脑马」。唯一禁死的是性格参数那两行——它们是难度标定的锚点，可写就连定性分类都不剩了。

「`dist` 对模块只读」那一行是里程制免疫刷卡的实现保证：只要没有任何模块能写里程，就不存在任何一张卡能凭空制造抽卡机会。这条比逐张卡去防可靠得多。

### 4.3 系统自持的效果实例

有些规则看起来是骨架的一部分，实际上必须能被卡牌关掉——目前是力竭惩罚（[玩法设计 §5](../game-design.md)），将来会有更多。**这类规则一律实现成系统自持的 `EffectInstance`**，挂载于比赛开始、`tags` 含 `system`，而不是写在模块里的 `if` 分支。

区别在可扩展性上，不在风格上：写成分支，则每加一张「关掉某条规则」的卡就在骨架里多一个布尔标记，第五张之后没人说得清这些标记的组合会产生什么；写成可移除的实例，加一张这种卡就是加一条按 tag 移除的数据声明，骨架一行不动。

`EffectInstance.tags` 因此是必需字段而非可选优化：`'buff' | 'debuff' | 'equipment' | 'env' | 'system'`。按 tag 查询与移除的 API 归骨架，写权限只给 `mod.suppress` 与 `mod.steal`。

## 5. 确定性与阶段顺序

模块化最容易丢掉的就是确定性，因此把代价写清楚：

- **模块执行顺序 = `id` 的字典序**，不是注册顺序，不是文件加载顺序。注册顺序会随打包器的模块解析变化。
- **模块清单与各自的 `version` 进 `rulesVersion`。** 加一个模块、改一个模块的行为，都是新规则版本；进行中的比赛用入场时绑定的版本。
- **模块不得持有跨 tick 的私有可变状态。** 一切状态放进骨架的状态容器，否则回放会因为模块实例被复用而不一致。
- **模块不得读系统时钟、不得 `Math.random`**，随机一律走骨架的域分离派生（[架构 §4](overall.md)）。

tick 内的阶段顺序在[架构 §5](overall.md) 已定，模块钩子的插入位置如下，该顺序同样是 `rulesVersion` 的组成部分：

```
超时 → 输入（onInputIntent）→ 效果更新（onEffectApply / onEffectExpire）
     → 模块速度贡献（contributeSpeed / contributeStamina，四算子分阶段聚合）
     → 电脑马目标速度 → 外部场与环境乘子、全局 clamp → 体力与速度
     → 位移 → 场与实体结算（field / hazard）→ 位置跳变（onPositionJump）
     → 里程与终点（onMileageMark / onHorseFinish）→ 发牌（onDrawRequest）
```

三条不能挪的顺序：

- **场与实体结算排在位移之后。** 炸弹判定的是这一 tick 走过的区间是否跨过弹点，按瞬时坐标相等判会在高速下漏判。
- **外部场乘子排在阻尼之后，并补一道全局 clamp。** 重力井刻意绕过 `tau` 与 `min_i`/`max_i`（理由见[玩法设计 §7](../game-design.md)），因此失去了性格参数那道钳制，必须在最外层兜住，否则场乘子会把速度推出可控范围。
- **里程结算排在位置跳变之后，但只累加自身位移。** 顺序上晚于跳变是为了让同 tick 内交换后的马用正确的位置做终点判定；里程本身不吃跳变。

## 6. 表现层：插槽与资源

[卡牌设计 §9](../card-design.md) 要求装备挂到马的不同部位。渲染侧的结构：

```text
src/game/rig/          马匹骨架与插槽定义，插槽随奔跑动画关键帧移动
src/game/attachments/  装备渲染器：按插槽挂载、装卸动画、层级与朝向
src/game/trail/        拖尾与拖影的历史位置队列
src/game/fx/           一次性特效：爆炸、重生闪烁、交换的镜头移动与换行
```

**渲染层订阅规则状态，规则层不知道渲染层存在。** 装备的挂载事件由规则的效果实例产生，渲染层每帧读取「当前有哪些装备实例」并做增量挂卸；它不需要事件通知，因此丢帧、暂停、重新挂载都不会让画面与规则失配。

`laneIndex` 是规则层的可变站位，交换时由 `mod.swap` 与 `pos` 一起置换；渲染层只读取它来决定马画在哪一行。**除相邻交换目标外，`laneIndex` 不得影响速度、里程或名次判定**，否则身份与表现边界会再次混淆。

资源缺失一律降级为占位，不阻断规则（[卡牌设计 §9.2](../card-design.md)）。**规则内核不 import 任何资源清单**，这是美术进度与数值调参解耦的唯一方式。

## 7. 目录结构

在[架构 §3](overall.md) 的基础上细化 `src/race/`：

```text
src/race/core/        骨架：tick 循环、运动学、体力、里程与终点、名次、RNG、效果容器、乘区、模块调度
src/race/cpu/         橡皮筋 AI（骨架的一部分，不是模块）
src/race/modules/     可插拔模块，一个目录一个模块，含各自的 L1 测试
src/race/cards/       卡牌定义表（纯数据）与卡池
src/race/__vectors__/ 确定性终态向量
```

卡牌定义是纯数据：**加一张卡的正常路径是往 `src/race/cards/` 加一条记录，不改 `src/race/core/` 一行。** 如果一张新卡逼着你改骨架，说明它需要第十类原语，先回[卡牌设计 §3](../card-design.md) 论证，再改架构，最后才加卡。
