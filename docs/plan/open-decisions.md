# 历史决策记录（不作为现行规则）

本文保留早期本地 Demo 的设计推导，包含已被废止的 gogo 节奏输入、电脑马橡皮筋和浏览器自报名次。不得把下文的“决定”用于有奖版本实现；现行规则只以[玩法设计](../game-design.md)、[卡牌设计](../card-design.md)及[链上架构](../architecture/onchain.md)为准。

## 0. 这份文档的判据

一条目进入本文的唯一理由是：**不定它就写不下去。** 三类明确排除，出现即删：

- 防作弊相关的任何设计。
- 数值平衡判断（某张卡是否过强、某个倍率该给多少）。只定「不定就无法构建」的基础量纲与结构，具体强度留给调参。
- 区块链证明、可验证性相关的任何设计。

每条给出**决定**与**理由**；我定不了的单列在 §6。已定的条目会同步写回对应主文档，本文只作决策记录，不作为规则出处。

## 1. 速度与体力模型（最大的缺口）

[卡牌设计](../card-design.md)与[效果系统架构](../architecture/effect-system.md)整体建立在一套模型上——速度带 `[vLow, vHigh]`、频率驱动加速度、等效频率 `f̂`、【力竭】回滞、体力 overcap——但[玩法设计 §5](../game-design.md) 写的还是旧的「三档区间给速度增益」。两者不是措辞差异，是两套不同的物理。卡牌设计里四处引用 `§5.2`/`§5.3`/`§5.4`/`§5.5`，玩法设计 §5 根本没有这些小节。

**决定：玩法设计 §5 按下面的模型重写并分小节，旧的三档增益表作废。**

### 1.1 速度带与加速度

| 量 | 含义 |
| --- | --- |
| `vLow` / `vHigh` | 速度带的下界与上界。卡牌改的是**带的位置**，不是速度本身 |
| `v` | 当前速度，由加速度积分得到，钳在带内 |
| `aMax` | 有输入时的最大加速度 |
| `aIdle` | 无输入时回落向 `vLow` 的加速度（负向） |
| `vHardMax` | 全局硬上限，严格大于任何马的 `max_i` 与玩家的 `vHigh` |

**理由：** 「卡牌改带、手改贴带多近」这条分工是卡牌设计 §3.2 的前提，也是节奏与卡牌互不吞噬的原因——卡牌给得再多，不点也贴不到 `vHigh`；点得再好，也超不过卡牌给出的带。旧模型里节奏直接加速度值，两者会互相稀释，调一边必然破坏另一边。

`vHardMax` 单独存在的唯一理由是外部场（重力井、天气）刻意绕过 `min_i`/`max_i`（[玩法设计 §7](../game-design.md)），失去了那道钳制，必须在最外层补一道。没有它，场乘子能把速度推到任意值。

### 1.2 节奏与等效频率

- 有效点击换算成一个**等效频率** `f̂ ∈ [0, 1]`，由最近若干次点击间隔与目标间隔的贴合度得出。
- `f̂` 驱动加速度：`a = aIdle + f̂ × (aMax − aIdle)`。
- `f̂` **不进速度乘区**。节奏改的是「多快够得着天花板」，不是天花板本身。

**决定：`f̂` 是节奏的唯一出口，B2 乘区为此永久留空。**

**理由：** 节奏一旦也能加速度带，它就和卡牌抢同一个池子，两条调参轴耦合死。留空的 B2 是一处显式的「此路不通」标记，比不写更能防止后来的人顺手往里加东西。

### 1.3 体力与【力竭】

- 体力按当前 `f̂` 消耗，按恢复速率回升，两者都走体力流水线（§2.2）。
- 体力触 0 进入**【力竭】**：速度带被压到 `vLow`，gogo 按钮锁死。
- **体力恢复到 30% 才解除力竭。** 这道回滞是必需的：没有它，体力会在 0 附近反复进出力竭，按钮一秒闪好几次。
- 体力允许 **overcap**：超出上限的部分只减不增，恢复不会把体力推回上限之上（【肾上腺素】）。

**决定：力竭实现为一个系统自持的 `EffectInstance`（`tags: ['system','debuff']`），不是体力模块里的 `if` 分支。**

**理由：** 【咖啡因过量】要关掉它。写成分支，每张「关掉某条规则」的卡就在骨架里多一个布尔标记；写成可移除的实例，加这种卡就是加一条数据声明。这一条[效果系统架构 §4.3](../architecture/effect-system.md)已经论证过，这里只是把力竭正式登记进去。

### 1.4 【死亡】的特殊通道

【死亡】不走速度流水线：它归零的是**速度本身**而不是速度带，并临时解除 `vLow` 下界直到速度爬回 `vLow`。恢复加速度不低于 `aMax / 2`，与玩家点不点无关。

**理由：** 不解除下界，`clamp` 会在下一帧把速度弹回 `vLow`，死亡就没有代价。保底加速度则是比赛能终止的唯一保证——力竭中死亡是最坏情况，此时 gogo 锁死，只能靠这条爬回去。

### 1.5 gogo 被占用时的 `f̂`

被 `Ability` 占用期间（拍手交换、风火轮），**`f̂` 锁定为 0.5**，不做实时判定也不归零。

**理由：** 归零会让屏幕上唯一的持续反馈突然消失；锁在一半保留了明确的机会成本——打得好的玩家在占用期间净亏，打得差的净赚。

## 2. 乘区定义

### 2.1 速度流水线

卡牌设计 §3.2 用了 B1、B3、C2 这些编号却没有完整定义过，effect-system §2 又提到「B1–B4 与体力两区」。补齐：

```
阶段 A   v_band += Σ add                        直接加算池
阶段 B   v_band ×= (1 + B1 + B2 + B3 + B4)      百分比加算，四个子池各自钳制
阶段 C   v_band ×= Π mul_j                      逐实例连乘
阶段 D   clamp(v_band, 硬下限, vHardMax)
```

| 子池 | 内容 | 钳制 |
| --- | --- | --- |
| B1 | 卡牌增益 | 按卡池上界 |
| B2 | **永久留空**（节奏走 `f̂`，见 §1.2） | —— |
| B3 | 外部场：重力井 | `[-0.6, +0.6]` |
| B4 | 环境：天气 | 按环境卡自身声明 |

**决定：B3 与 B4 分开，不合并。**

**理由：** 合并就没法单独钳制。重力井最高 ±60%、天气 ±10%，同一个池子里只能取一个上限，要么天气被过度放宽、要么重力井被过度收紧。

### 2.2 体力流水线

同样三阶段，但有两个独立的 `target`：

| target | 含义 | 当前使用者 |
| --- | --- | --- |
| `staminaCost` | 消耗速率 | 火箭喷射器（`mul` 0.5） |
| `staminaRegen` | 恢复速率 | 望梅止渴（`padd` +100%） |

**决定：卡牌设计里的「C2 区」是笔误，指的是 `staminaCost` 的 `mul` 阶段。全文替换。**

### 2.3 算子只有三种

`ModifierDecl.op` 当前声明了 `add | padd | mul | pmul`，但 `pmul` 从未被定义，也没有任何一张卡用它，而卡牌设计 §3.2 的标题写「三种算子」、正文写「四种算子」。

**决定：删除 `pmul`，算子固定为 `add | padd | mul` 三种。**

**理由：** 它与 `mul` 的差别说不清楚。一个说不清语义又无人使用的算子，留着只会让后来的人猜它该用在哪。

### 2.4 电脑马走同一条流水线

电脑马也真的吃卡（[玩法设计 §7](../game-design.md)），但它没有速度带，只有 `base_i`。

**决定：同一条 A/B/C/D 流水线，输入换成 `base_i`，输出即有效基础速度。公式里的 `base_i + card_i` 正式改写为 `base_eff_i = pipeline(base_i, 该马的效果实例)`。**

**理由：** 两份实现意味着同一张加速卡对玩家和对电脑马的结算方式可以悄悄分叉，而这种分叉在批量模拟里表现为「手感指标怎么调都对不上」，极难定位。外部场那一路仍然不走流水线，它绕过阻尼直接乘在目标速度上——那是刻意的，理由在玩法设计 §7。

## 3. 结构性矛盾

### 3.1 赛道行号：规则量还是渲染量（最硬的一条）

三处文档互相打架：

- [玩法设计 §2](../game-design.md)：赛道不是身份，规则层从不读赛道。
- [效果系统架构 §4.2/§6](../architecture/effect-system.md)：行号是纯渲染量，**不得反向影响任何规则判定**。
- [卡牌设计 §6.1](../card-design.md)：【交换】的目标是**画面上相邻的上下两行**。

第三条直接违反前两条：目标选择是规则判定，而它读了行号。

**决定：引入 `laneIndex`，它是规则状态，与 `horseId` 分离。**

| 概念 | 性质 | 可变 | 用途 |
| --- | --- | --- | --- |
| `horseId` | 身份 | 否 | 性格参数分配、同 tick 冲线的兜底排序 |
| `laneIndex` | 站位 | 是，只由【交换】改 | 交换的相邻判定、炸弹归属、渲染画在第几行 |

渲染层按 `laneIndex` 画，不再持有自己的行号。「赛道不是身份」这句话保持成立——身份是 `horseId`，`laneIndex` 只是站位。

**理由：** 另外两条路都更糟。把交换目标改成「按 `pos` 排序的相邻马」会让这张卡失去「上下行」的直观读法，玩家看不出自己会和谁换；把行号整个升格为身份则推翻名次兜底排序，改一次开局布局就改掉名次。分离身份与站位是唯一两边都不破的解法，代价只是多一个规则字段。

**连带结论：炸弹按 `laneIndex` 归属。** 卡牌设计 §7.1 说「炸弹可以炸到触发者（通过【交换】切换了赛道）」——只有炸弹绑在站位上这句话才成立。绑在 `horseId` 上的话触发者永远踩不到自己放的弹，那句话就是错的。

### 3.2 【交换】换不到终点

[卡牌设计 §6.1](../card-design.md) 同时写着「已冲线的马不作为交换目标」和「最后一秒把自己换到终点前是这张卡的设计高光」。前者成立时后者做不到：能换到的最远位置就是某匹未冲线的马的 `pos`，必然 `< L`。

**决定：保留「已冲线的马不作为目标」，把设计高光的表述改为「换到一匹领先马的位置」。**

**理由：** 允许换到已冲线的马会引出一串新问题——那匹马换到哪去、它的名次算不算数、尾场怎么跑。而「把自己弹到领跑者身边」本身已经是足够强的戏剧性，不需要靠直接冲线来兑现。

### 3.3 电脑马的牌从哪来

[玩法设计 §3](../game-design.md) 只说「电脑马独立选牌，牌不从玩家牌堆取，同一匹马一场内不重复」，[§4](../game-design.md) 说「按固定策略立即选牌」。这个「固定策略」没有任何定义，而电脑马能抽到炸弹、交换、天气——这些会打到玩家身上。

**决定：每匹电脑马一副 3 张的私有牌堆，由 `H(seed, "cpudeck", horseId)` 从全卡池无放回派生；到里程档就按顺序取第 k 张直接生效。没有三选一，没有刷新，没有策略。**

**理由：** 电脑马不需要决策。给它一个「固定策略」就是给项目引入一个谁都不会去调、却会影响手感指标的参数。一副按序消费的私有牌堆行为完全确定、可复现，且天然满足「同一匹马一场内不重复」。

**连带：** 电脑马抽到纯玩家向的卡（发牌修正、外观）时该怎么办——见 §6.2，这条我定不了。

### 3.4 【视野剥夺】是孤儿状态

[卡牌设计 §4](../card-design.md) 定义了两个状态：【视野剥夺】Blinded（只作用于渲染）和【目中无人】Blinded—pro（也作用于规则）。但 C-21【理解孙学】用的是后者，前者没有任何卡使用。

**决定：删除【视野剥夺】，只保留【目中无人】。**

**理由：** 一个没有卡使用的状态词条会被后来的人当成可用积木，而它和【目中无人】的区别只在一句话，极易误用。需要时再加回来的成本是零。

### 3.5 【起风了】不是「棋盘状态卡」

卡牌设计 §7.4 称它为棋盘状态卡，因为「可能对自己是负的、对对手是正的」。但风是**全局同向**的，只作用于【起飞】的马——所有起飞的马同时 −10% 或同时 +10%。它不制造玩家与对手之间的不对称，只制造「我此刻在不在天上」的不对称。

**决定：保留机制，改掉描述。它是一张条件增益/减益卡，条件是【起飞】，方向随机。**

**理由：** 描述准确与否直接影响后续卡牌的设计方向。把它当「棋盘卡」，后面会照着这个方向加更多全局卡，但真正的棋盘性质（有人受益有人受损）一张都没做出来。

## 5. 交付计划的重划

[demo 计划](demo.md)的 D3 写的是「14 张牌堆 + 游标发牌 + 卡面三段动画 + 效果原语与卡牌清单」。文档现在的规模是 **21 张卡、9 类原语、18 个模块**，这不是一个阶段。

**决定：D3 拆成三段，按原语复杂度而不是按「卡牌」这个整体切。**

| 阶段 | 内容 | 为什么单独成段 |
| --- | --- | --- |
| D3 发牌与选牌 | 牌堆、游标、刷新、慢放、20 秒限时、卡面三段动画。**效果全部 mock 成空实现** | 选牌流程能独立验收：面板出得来、限时准、刷新对、回放一致 |
| D4 效果骨架 + 三类原语 | `EffectInstance` 容器、`tags`、乘区聚合、模块调度；`Modifier` / `Status` / `Trigger` | 这三类覆盖全部纯数值卡与状态卡，且不需要场上实体、不需要渲染插槽 |
| D5 重原语 | `Equipment` / `Ability` / `Hazard` / `Field` / `Environment` / `DrawRule`，含 rig 插槽与装备挂载 | 每一类都要动渲染层结构，和前面是不同性质的工作 |

原 D4/D5 顺延为 D6 完整动线、D7 调参打磨。

**理由：** 按「卡牌」切会让一个阶段同时碰规则容器、渲染插槽、赛道实体和 UI 面板，任何一处卡住整段都验收不了。按原语切，每段的产出都能独立跑起来，也能独立回归。

### 5.1 确定性向量的构造方式

[效果系统架构 §5](../architecture/effect-system.md) 要求向量「每组至少触发一次死亡、一次交换、一次炸弹、一次重力井、一次刷新、一次天气替换、一次装备转移」。但这些卡未必进得了牌堆——21 张里只抽 14 张。

**决定：向量测试用注入式牌堆，直接构造 `deck` 数组绕过 seed 发牌。该入口仅测试可见。**

**理由：** 靠搜索 seed 去凑出「同时包含这七张卡」的牌堆，既慢又会在卡池变动后全部失效。发牌派生本身另有自己的向量测试覆盖，两件事不该耦合在一组用例里。

## 6. 我定不了的

### 6.1 数值（明确排除在本文之外，但列出它们阻塞什么）

| 未定值 | 阻塞 |
| --- | --- |
| 基础速度、`vLow`/`vHigh`/`aMax`/`aIdle`、赛道长度 `L` | D1 就需要。**这是最优先的一组**，没有它规则内核只能写结构不能跑 |
| 体力上限、消耗与恢复速率、力竭阈值 | D1 |
| 重力井作用半径 `R` | D5 |
| 【薄肌】系列 `add` 的量级 | 依赖基础速度，D4 |
| 各卡的时长与倍率 | D4 起，可边调边走 |

第一行是唯一真正卡住开工的：其余都可以先填一个能跑的占位值，在批量模拟里调。

### 6.2 电脑马抽到玩家向的卡

按 §3.3，电脑马从全卡池抽 3 张。但卡池里有只对玩家有意义的卡：【选择困难综合症】【最后的波纹】【海贼王的宝藏】改的是选牌面板，而电脑马没有面板；【黄毛】【染成绿的】是外观；【理解孙学】的视野剥夺对 AI 无意义。

三条路，各有代价，我选不了：

1. **给卡加 `cpuUsable: false`，电脑马的牌堆只从可用子集抽。** 干净，但卡池被切成两半，且要逐张标注。
2. **电脑马抽到就空过。** 零成本，但玩家会看到对手抽卡什么也没发生。
3. **电脑马用独立的小卡池（只含通用增益卡）。** 最可控，但对手永远不会炸你、不会和你换位置，失去一半戏剧性。

倾向第 1 条，但它决定了卡表要不要加一列，属于结构变更，等你拍。

### 6.3 【版本答案】的触发率

按当前结构算：卡池 21 张、牌堆 14 张、玩家不刷新时只看得到前 9 张、三张构件必须分属三次不同展示。

- 三张构件同时进入 `deck[0..11]`：约 27.5%（【理解孙学】【薄肌 pro】是 rare，有 1/6 概率被抽去当保底末两张，进不了前段）
- 给定都进了，三张分属三个不同展示组：27 / C(12,3) ≈ 12.3%
- **合计约 3.4%**，即大约每 30 局有一局**存在**触发的可能，玩家还得三次全选垃圾牌。

这是结构事实不是平衡判断，所以列在这里而不是 §6.1。要让它更可遇见，能动的结构有两处：把三张构件全部设为 `common`（避开保底位，约升到 4.5%），或把判定从「三张」放宽到「两张」。**都改变设计意图，我不替你选。**

### 6.4 卡牌英文名

21 张卡的名字几乎全是中文梗：【薄肌】【理解孙学】【版本答案】【顺手牵羊】。这些梗翻译不过去——直译丢梗，意译丢名。

**demo 阶段的处理我可以定：** i18n 框架与 UI 文案全量做，卡牌英文名先用直译占位并标 `//TODO`，切到 en 不会崩、只是卡名生硬。**但最终怎么处理要你定**，因为这关系到这个游戏面向谁。

### 6.5 卡牌图鉴要展示什么

首页有「卡牌图鉴」入口，但从没定义过内容。至少三种做法：全卡池只读展示 / 只展示玩家见过的卡（需要本地收集进度）/ 带梗源与出处的完整词条。第二种最有留存价值也最费事，第一种一天能做完。
